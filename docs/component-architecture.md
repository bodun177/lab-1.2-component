# Компонентна архітектура «Автозапчастини»

Документ фіксує межі відповідальностей, ієрархію та контракти компонентів
після лабораторної роботи 1.2.

## Ієрархія відображення

```
App
└── AppLayout                     (title, links, children)
    ├── SiteHeader                (title, links)
    │   ├── Title                 (children) — h1
    │   └── MainNav               (links)
    ├── main
    │   ├── HomePage              (маршрут /)
    │   │   ├── Section           (про застосунок)
    │   │   └── Section           (каталог)
    │   │       ├── CatalogSummary (total)
    │   │       └── PartList      (items)
    │   │           └── PartCard  (item) — для кожного запису
    │   │               └── AvailabilityBadge (available)
    │   │           └── EmptyState (якщо список порожній)
    │   ├── SelectionPage         (маршрут /selection, part)
    │   │   ├── Section           (підбір за автомобілем)
    │   │   │   └── PartSelectionFormPreview (idPrefix, categories)
    │   │   │       ├── FormField (для кожного поля)
    │   │   │       └── AppButton (кнопки)
    │   │   └── Section           (приклад результату)
    │   │       └── PartCard      (item)
    │   └── AboutPage             (маршрут /about)
    │       └── Section
    └── footer
```

`AppLayout` не імпортує сторінки: вони надходять через `children` з `App`.
`PartCard` використовується на двох сторінках, тому картка не знає ні про
маршрут, ні про джерело даних.

## Контракти ключових компонентів

| Компонент               | Вхідні властивості                       | Домовленість                                                        |
| ----------------------- | ---------------------------------------- | ------------------------------------------------------------------- |
| `AppLayout`             | `title`, `links`, `children`             | створює єдиний `main`, шапку й підвал                               |
| `SiteHeader`            | `title`, `links`                         | містить h1 застосунку та навігацію                                  |
| `MainNav`               | `links`                                  | масив `{ to, label }`; `to` — маршрут React Router                  |
| `Section`               | `id`, `title`, `children`                | `id` унікальний у документі, заголовок отримує `${id}-title`        |
| `PartList`              | `items`                                  | масив записів; порожній масив допустимий                            |
| `PartCard`              | `item`                                   | коректний запис `part` з `src/data/parts.js`                        |
| `AvailabilityBadge`     | `available`                              | логічне значення, без зміни даних                                   |
| `CatalogSummary`        | `total`                                  | число записів у каталозі                                            |
| `PartSelectionFormPreview` | `idPrefix`, `categories`              | унікальний префікс `id`; макет без збереження даних                 |
| `FormField`             | `id`, `label`, `hint`, `children`        | вкладене поле має той самий `id`; за наявності `hint` — `aria-describedby` |
| `AppButton`             | `children`, `type`, `variant`, `disabled`| `variant`: `primary` або `secondary`; тип за замовчуванням `button` |
| `EmptyState`            | `title`, `children`                      | текст порожнього стану задає місце використання                      |
| `Title`                 | `children`                               | h1 застосунку, стилі через styled-components                        |

## Прийняті рішення

### 1. Спільна секція замість копіювання розмітки

`Section` використано чотири рази: опис і каталог на головній, підбір і
результат на сторінці підбору, відомості на сторінці «Про застосунок».
Секція відповідає лише за заголовок, `id` і зв'язок `aria-labelledby`, а вміст
надходить через `children`. Додавання нової секції не потребує нового
компонента й не змінює наявні.

### 2. Одне правило наявності в одному місці

Підпис і клас статусу обчислюються лише в `AvailabilityBadge`. Картка каталогу
та сторінка підбору показують статус однаково: зміна тексту «Є в наявності»
виконується в одному файлі й з'являється в обох місцях.

### 3. Картка як повторно використовуване подання

`PartCard` отримує готовий запис і не імпортує масив, не шукає запис за
індексом і не знає про маршрути. Завдяки цьому та сама картка показує елемент
каталогу та приклад результату підбору.

### 4. Збережена маршрутизація Л 1.1

У Л 1.1 застосунок уже використовував React Router, тому маршрути `/`,
`/selection` і `/about` збережено, а сторінки підключено як елементи `Route`.
`MainNav` працює з `to`, а не з `href`, щоб перехід не перезавантажував
сторінку. Повне опрацювання маршрутів і параметрів адреси належить до Л 2.2.

### 5. Оформлення

Основне оформлення — власні CSS класи в `src/index.css`: вони прості для
перевірки й не додають залежностей. `styled-components`, підключений у Л 1.1,
залишено лише для заголовка застосунку (`Title`), щоб не переписувати наявний
компонент без потреби. React Bootstrap не підключався: базових стилів
достатньо, а зайва бібліотека ускладнила б узгодження з наявними правилами.

## Напрям залежностей

```
pages → components (parts, selection, ui), data
components/parts → components/ui
components/selection → components/ui
components/ui → зовнішні бібліотеки
data → нічого
```

Спільні UI компоненти не імпортують сторінки, дані або предметні компоненти.
Сторінка — єдине місце, де локальні дані зустрічаються з поданням; у Л 3.2
достатньо замінити імпорт масиву на результат роботи сервісу, не змінюючи
контракти `items` і `item`.

## Точки розвитку

- **Л 2.1** — стан вибраної запчастини, керовані поля підбору, пошук і фільтри;
  `AppButton` отримає `onClick`, `PartSelectionFormPreview` — `value`/`onChange`.
- **Л 2.2** — маршрут `/parts/:id` для окремої сторінки запчастини.
- **Л 3.1** — форма замовлення з валідацією та операціями над записами.
- **Л 3.2** — асинхронне джерело даних замість `src/data/parts.js`.
